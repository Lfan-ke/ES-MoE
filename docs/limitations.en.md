## Divergence from upstream and from the paper

This package reimplements the structure of YOLO-Master's `ES_MOE`. Three differences are worth stating after a line-by-line comparison.

**The balancing term: the paper and upstream agree, and this package read the wrong tensor.** Upstream applies `N * sum(usage^2)` to whatever `DynamicRoutingLayer` returns, and in training that is the output of `_soft_top_k` -- **the gate, after the top-k mask and renormalisation**. The paper's equation 12 averages the same thing. The two are therefore one objective up to an affine map: `sum((mu - 1/E)^2) == sum(mu^2) - 1/E`, so `L_paper = (L_upstream - 1) / E^2`, with the same minimiser and proportional gradients.

This package first wrote `gshard_balance` against the **raw softmax**, which is neither. It now reads the gate, and a test pins the identity above. The probability-reading form survives as `gshard_probs_balance` to isolate one variable -- whether the objective reads the probabilities or the dispatch. That, not the choice between the Switch and GShard formulas, is what decides whether a routing collapse is visible to the term.

The coefficient still differs: upstream carries `balance_loss_coeff = 1.0` against this package's `weight = 0.01`. But upstream also divides by an EMA of the term itself and caps the sum at `aux_budget = 3.0`, so its steady-state contribution is about `1.0 * gain` and the coefficient mostly moves the transient. An earlier note here claimed a 31x difference in balancing gradient without accounting for that; it is corrected.

**The paper describes a diversity objective that the shipped block does not apply.** The paper (arXiv 2512.23273) says training carries an objective encouraging complementary expertise. Upstream does define `diversity_loss_coeff`, but it belongs to a different family of blocks, defaults to `0.0`, and `ES_MOE` never references it. Nothing in the default configuration pushes the experts apart - which is consistent with the absence of scale specialisation measured here across seven generations, and is not particular to this package.

**How far inference sparsifies is a parameter; the default differs.** Upstream's `dynamic_threshold` is 0.4, pruning low-confidence experts at inference -- the leading one is kept whatever its share, and the survivors are renormalised. This package implements the same rule but defaults to `0.0`, pruning nothing: every record in `results/` was measured that way, and changing the default would make them incomparable. Pass `dynamic_threshold=0.4` to reproduce upstream; `sparse_inference=False` matches its `use_sparse_inference=False`.

**The graft location matches the paper's final default; the count does not.** Section 3.1 of the paper places the block in both backbone and neck, but the ablation in section 4.3.1 (Table 5) reports Neck Only 58.2, Both 54.9 and **Backbone Only 62.1**, on which the authors state "we adopt backbone-only ES-MoE as our default configuration". This package grafts into the backbone only, which agrees with that default; an earlier note here said the paper used both placements and was written without that table.

The count does differ: upstream's yaml places one block after every backbone stage, four in all, where this package defaults to one at the backbone end. `graft(at="backbone_stages")` reproduces the upstream layout and yields four blocks on all seven generations. The stage boundaries are derived from the downsampling layers rather than fixed indices, because the generations disagree on how they downsample -- v9 uses `AConv`, v10 `SCDown`, the rest a stride-2 `Conv`.

**Two differences inside the block, both switchable here.** Upstream applies a `BatchNorm2d + SiLU` after the weighted sum (the `Norm(·)` of the paper's equation 2); this package has none by default, and `out_norm=True` adds it. Upstream runs every expert while training -- an unrouted one is weighted zero but its normalisation statistics keep moving -- while this package skips unrouted experts, freezing those statistics; `dense_training=True` matches upstream. Neither is the default: each could change the conclusion about routing collapse, and settling them before there is a controlled comparison would be argument standing in for data.

**Block settings live in the config, not on the instance.** The trainer rebuilds the model from `model.yaml`, so an objective or a switch set on the blocks after `YOLO(cfg)` returns disappears with the instance that is discarded -- with no error and no trace. `graft()` therefore writes the settings into the config (`[4, 2, null, {balance: …, out_norm: …, dense_training: …}]`), and `ESMoE` takes them as an options mapping, resolving an objective by name. The block configuration `scripts/train.py` records is read off the trained model rather than repeated from the command line, and the run refuses to start when the two disagree. `scripts/blockspec.py` reads back what was in force from any checkpoint.

Checked and identical: the default heterogeneous kernels for four experts are `[3, 5, 7, 9]` in both; both routers are a two-layer bottleneck after global pooling (`reduction = 8`, floored at 8 channels); both clamp logits to `[-30, 30]` before the softmax; and the paper's Soft Top-K (equation 8) matches this package's gating term for term.

## Against the paper's own claims

The section above compares this package with upstream's source. The paper's text makes further claims that can be checked, and this is what was measured against each. **Every line below holds only within this project's scope**: VisDrone, nano backbones, 120 epochs from scratch, one card. The paper's numbers come from five benchmarks and a full training recipe. So this is not "failed to reproduce"; it is "under these conditions, the mechanism is not visible".

| the paper's claim | what was measured here |
|:--|:--|
| The routing network guides expert specialisation, with 3x3 / 5x5 / 7x7 capturing distinct multi-scale patterns | Across 108 block analyses the correlation between routing probability and object size runs from −0.49 to +0.59, 232 positive against 200 negative, and **changes sign across seeds**. The dominant expert's kernel is any of the four (kernel 3 twelve times, 5 twenty-five, 7 thirty-two, 9 thirty-nine) and moves with the seed. No stable division by scale. |
| Simple regions activate fewer experts; complex regions reach more capacity | The number activated in training is **always k**, independent of the input — that is what top-k means. The only input-dependent count is inference-time pruning by `dynamic_threshold` (0.4 upstream). So "capacity by complexity" does not hold during training, and at inference it rests on one threshold. |
| Load-balancing supervision prevents expert collapse and keeps utilisation uniform | Two layers. **Keeping experts alive: this package's Switch term does, the paper's objective does not.** The paper has no run without the term; this project added one, three seeds each on v5n and v10n, and all six checkpoints lose two experts. The Switch term at 0.01 leaves no dead expert in 66 checkpoints. The paper's eq. 13 and upstream read the gate renormalised over the top-K, which has exactly zero gradient for experts outside it; five of six such checkpoints have a dead expert, also at 1.2 to 3.0 times Switch's pressure. **Keeping utilisation uniform: neither does.** Under the Switch term the leading expert takes 0.47 to 0.94 of the top-1 choices across 84 block analyses, and the top two take 1.24 to 1.78 of 2.0. |
| The block goes into both backbone and neck (section 3.1) | The paper's own Table 5 makes backbone-only the default (62.1 against 54.9 for Both). This package agrees with that default. |
| One block after each backbone stage, four in all (upstream's yaml) | Reproducing that layout with `at="backbone_stages"` gives a paired mAP50 of **−0.0071** on v10n (0/3) and **−0.0049** on v5n (0/3), with mAP50-95 at 0/3 on both. Four blocks sum four auxiliary terms, so at one weight the total is fourfold; cutting each block to 0.0025 so the total matches one block gives **−0.0113** on v10n (0/3), and a mAP50-95 interval of [−0.0132, −0.0018] that excludes zero. The count costs, not the pressure. The direction agrees with the paper's own Table 5, where Both costs 5.9 points: **more ES-MoE is worse, not better.** |
| An objective encouraging complementary expertise (abstract) | Upstream's `diversity_loss_coeff` belongs to a different block family, defaults to `0.0`, and `ES_MOE` never references it. Nothing in the default configuration pushes experts apart, which is consistent with the row above. |
| Soft Top-K (eq. 8) in training, hard Top-K (eq. 9) at inference | Mathematically identical, and verified: a softmax over the top-K subset equals a full softmax masked and renormalised. This package matches eq. 8 term for term. |
| "The largest gains appear on VisDrone (+2.1%) ... validating our design for small object detection" | The architecture comparison is not tested here, but **the direction by size is**. Split into COCO buckets on VisDrone, both positive arms gain on **medium and large** objects and sit flat on small: `norm` gives APs +0.0001, APm +0.0042, APl +0.0137; `dense` gives APs +0.0000, APm +0.0052, APl +0.0081; the default arm APs +0.0031, APl +0.0048. The four-block arm is negative in every bucket on v10n (APs −0.0029, APm −0.0048, APl −0.0016) and on small and medium objects on v5n (APs −0.0038, APm −0.0047), with large at +0.0046. **Under these conditions what the block buys on VisDrone is not small objects.** |

**What this section is for**: it separates what the paper claims from what an independent implementation can observe under controlled conditions. The rows that come up empty point at how observable the mechanism is — routing collapse, no division by scale, more blocks doing worse — not at a refutation of the authors' conclusions. Refuting those would mean reproducing at their scale, which is beyond this project's compute and scope and is recorded in [limitations](limitations.md).
